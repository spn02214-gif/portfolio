01

발굴한 문제

Problem 01 · Urgency Gap
긴급 요청 대응 공백

ERP가 "capacity 없음"을 표시해도 담당자는 비공식 네트워크로 처리. 매주 반복되는 패턴이지만 시스템에 기록되지 않아 누적 학습 불가. 긴급 전환율 40%+ 고객사가 존재함에도 사전 감지 체계 없음.

Problem 02 · Data Scatter
업무·보고 체계 분산

채팅·이메일·Teams·ERP 4개 채널에 정보가 분산. 누락·오류 발생 시 원인 추적 불가. 기존 ERP는 조회 기능만 있고, 기존 솔루션은 실제 운영 환경의 워크플로우와 맞지 않음.

Problem 03 · Visibility
현장 실무 가시성 부재

ERP 데이터는 있지만 "지금 뭐가 위험한가"를 한눈에 보는 레이어가 없음. 월말 선적 집중, 리드타임 단축 패턴 등 반복적 신호를 수동으로 감지 중.

현장에서 직접 관찰한 것
  • →담당자가 ERP 말고 메신저로 먼저 확인한다
  • →긴급 처리 여부가 담당자 개인 기억에 의존한다
  • →월말마다 "이번 달 선적 어떻게 됐어요?"를 반복한다
핵심 판단

문제의 본질은 데이터 부족이 아니다.
"이미 있는 데이터를 판단 가능한 형태로
해석하는 레이어의 부재"

공통 구조적 원인

ERP 교체 사이클 2~3년 + 임원급 결재 구조 → 현장 속도와 시스템 업데이트 속도의 갭.
해결 방향: ERP를 교체하는 게 아니라 옆에 붙이는 경량 레이어.

02

핵심 결정 6가지

각 결정은 왜 그 선택을 했는가와 무엇을 포기했는가를 함께 기록합니다. 제약 조건 안에서의 판단이 설계를 만든다는 것을 이 프로젝트를 통해 체득했습니다.

결정 왜 이렇게 결정했는가 포기한 것 (Trade-off)
ERP 교체 대신 경량 레이어 ERP 교체는 의사결정 2~3년 + 임원급 결재. "ERP 교체 없이 도입"이 보수적 조직의 핵심 설득 포인트. 실시간 데이터 동기화
→ 엑셀 업로드 주기 의존
엑셀 업로드 기반 MVP 현장 인터뷰 결과: "ERP에서 복붙해서 엑셀 저장"이 실제 워크플로우. 기존 습관 유지 = 도입 저항 최소화. 실시간성
→ API 연동은 Phase 2
Risk Score 기반 판정 단순 조건(납기 지남 → 지연)으로는 복합 상황 미반영. 점수 합산 방식은 AI 입력값으로도 활용 가능. 단순성
→ 복잡성 증가 감수
Sale Order 1개 시트만 있어도 작동 4개 시트 강제 시 도입 장벽↑. 단계적 도입: Sale Order → + Shipment List 순서로. 오탐은 "Unknown" 뱃지 + 배너로 명시. 출하 정확도
→ 데이터 없으면 Unknown 표시
localStorage → API 교체 가능 구조 팀 공유는 검증 전에 만들면 낭비. 단, appendEvent() 내부 한 줄만 교체하면 전환되도록 설계. 팀 실시간 공유
→ Phase 2에서 API 전환
데이터 모델 / 평가 / UI 3단 분리 ERP API 연동 시 mapRawToOrder()만 교체, 서버 사이드 평가 전환 시 evaluateOrder()만 이동. 레이어 독립성 확보. 초기 구현 단순성
→ 구조 복잡성 증가

Risk Score Formula
riskScore = 50 (overdue) + 30 (imminent ≤2d) + 20 (short lead ≤3d) + 10 (not shipped) + 40 (urgent flag)
→ 0–29: Normal · 30–59: Warning · 60+: Critical
→ 복합 조건을 하나의 우선순위 판단 기준으로 압축

05

판단의 흐름 — 무엇이 달라졌는가

이 프로젝트의 판단 흐름
① 문제
ERP 데이터는 있지만 "지금 어떤 주문이 위험한지" 즉시 판단할 수 없는 상태. 담당자가 비공식 채널로 처리하며 누락·반복이 발생.
② 관찰
문제의 원인은 데이터 부족이 아니라 "해석 레이어의 부재". ERP를 교체해도 해결되지 않는 구조적 문제.
③ 판단
ERP 교체(2~3년 사이클) 대신 기존 엑셀 워크플로우를 유지하면서 위험도를 자동 계산하는 경량 레이어를 선택. 도입 저항 최소화가 핵심 기준.
④ 실행
납기·긴급도·리드타임·출하 여부를 가중합산한 Risk Score 모델 설계. 실제 ERP 데이터(211건) 연동 검증. 2개국 언어 지원으로 현지 팀 활용 가능성 확보.
⑤ 결과
업무 판단 구조 전환
ERP 조회 → 담당자 수동 판단 → 대응 결정 구조를
엑셀 업로드 → 리스크 자동 정렬 → 즉시 대응 구조로 전환

반복 문제 사전 식별 가능
긴급률 40%+ 고객사 패턴을 수동 기억이 아닌
데이터 기반으로 사전 감지 가능

사용자 중심의 실행 구조 확보
담당자가 ERP를 수작업으로 탐색하던 과정을
업로드 직후 우선 대응 대상을 바로 식별할 수 있는 상태로 전환
Constraint-Based
01
제약 조건이 설계를 만든다
ERP 접근 불가 — 이 제약이 엑셀 업로드·로컬 저장·단계적 도입 구조를 만들었다. 제약은 장애물이 아니라 설계 기준이다.
AI as Layer
02
AI 제공자는 바뀌지만 구조는 남는다
Gemini → Azure OpenAI 교체를 환경변수 한 줄로 설계. 중요한 건 어떤 AI를 쓰느냐가 아니라, 어떤 데이터를 어떤 형태로 AI에 연결하느냐다. Risk Score가 AI 입력값이 되도록 파이프라인을 선행 설계했다.
Validation First
03
배포보다 반응이 먼저다
"팀이랑 같이 실시간으로 보고 싶다"는 반응 1건을 Phase 2 착수 조건으로 설정했다. 코드가 완성돼도 쓸 사람이 없으면 제품이 아니다. 검증 조건을 먼저 정의하고 개발한다.
PM's Role
04
PM의 역할은 기술이 아니라 설계다
기술로 문제를 해결하는 게 아니라, 조직의 제약 조건 안에서 실행 가능한 구조를 설계하는 것. mapRawToOrder → evaluateOrder → render 3단 분리는 지금이 아니라 다음 단계를 위해 만들었다.
User Signal
05
사용자 반응 기반 검증 단계 진입
초기 테스트 과정에서
“이거 있으면 매번 ERP를 뒤지지 않아도 되겠다”는 반응을 확인했다.

기능 완성 자체보다 반복 사용 가능성을 기준으로
Phase 2 진입 여부를 판단하도록 설계했다.
