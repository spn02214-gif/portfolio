ERP 데이터를
실행 우선순위로 전환한 Decision Layer 설계

"ERP가 기록한 주문 데이터를
리스크 탐지 → 우선순위 판단 → 실행 액션으로 연결하는
경량 Execution / Decision Layer 설계"

ERP는 주문 이력을 보관하는 기록 시스템이지만, 현장에는 지금 무엇부터 대응해야 하는지 판단하는 흐름이 부족했습니다. 이 프로젝트는 실제 주문 데이터를 기반으로 Decision Layer를 정의하고, 리스크 탐지부터 행동(Action)까지 연결한 MVP 검증 사례입니다.

01

Problem — ERP와 실행 사이의 공백

Problem 01 · Decision Delay
ERP는 기록하지만, 무엇부터 처리할지는 말해주지 않는다

주문·납기·출하 정보는 있지만, 지금 확인할 대상을 바로 알려주지 못했습니다. 리스크 판단은 개인 경험과 기억에 의존했습니다.

Problem 02 · Execution Gap
조회 이후의 실행 흐름이 분산되어 있다

실제 대응은 채팅, 이메일, Teams, 개인 메모로 흩어졌습니다. 누락·지연·긴급 전환의 원인도 추적하기 어려웠습니다.

Problem 03 · Risk Visibility
반복되는 리스크 신호가 행동으로 연결되지 않는다

월말 선적 집중, 짧은 리드타임, 긴급 전환 고객사 같은 신호는 존재했습니다. 하지만 사전에 대응 순서를 정하는 구조는 없었습니다.

Insight

핵심 문제는 데이터 부족이 아니라, 기록 데이터를 실행 우선순위로 바꾸는 중간 레이어의 부재였습니다.

02

Solution Structure — 의사결정 흐름 설계

기록 데이터를 리스크 신호로 해석하고, 대응 순서와 후속 액션으로 이어지게 재구성했습니다.

설계 결정 비즈니스 판단 운영적 의미
ERP 위에 Decision Layer 배치 기존 시스템은 유지하고, 현장 판단에 필요한 해석 흐름만 보완했습니다. 도입 저항 감소
기존 엑셀 업무 흐름 유지 현장에 이미 존재하는 엑셀 추출 습관 위에서 빠르게 검증했습니다. 빠른 검증 가능
리스크 신호를 점수화 납기, 리드타임, 출하 여부, 긴급 플래그를 하나의 기준으로 통합했습니다. 수동 판단 축소
탐지 → 판단 → 실행 흐름 분리 리스크 확인에서 멈추지 않고 담당자 액션과 기록까지 이어지게 했습니다. 운영 흐름 명확화

Risk Prioritization Logic
Priority = overdue + imminent due date + short lead time + not shipped + urgent flag
→ 0–29: Normal · 30–59: Warning · 60+: Critical

Impact — 무엇이 달라졌는가

성과는 기능 수가 아니라, 주문 운영의 판단 방식이 바뀐 데 있습니다.

ERP 조회 중심 업무를 우선순위 판단 구조로 전환
전체 주문을 훑는 방식에서 먼저 확인할 대상을 분리하는 방식으로 전환
Impact
반복 긴급 전환 고객사 패턴 식별 및 사전 대응 분리
반복적으로 긴급 전환이 발생하는 고객사를 사전 대응 대상으로 분리
Validated
211+건의 실제 ERP 주문 데이터로 판단 기준 검증
실제 운영 환경의 주문 라인에 적용해 분류 기준을 확인
Evidence
분석에서 끝나지 않고 행동(Action)까지 연결
위험 주문 식별 후 담당자 확인, 메모, 인수인계 흐름으로 연결

대규모 전환 없이 기존 엑셀 기반 업무 흐름 위에서 검증
Low Friction
05

Implementation — 실행 가능한 구조로 전환

Constraint-Based
01
제약 조건이 설계를 만든다
ERP 교체가 어려운 조건을 전제로, 기존 업무 흐름 위에 붙는 단계적 도입 구조를 선택했다. 제약을 설계 기준으로 사용했다.
Validation First
02
확장보다 검증이 먼저다
초기 반응은 “팀과 같이 보고 싶다”였습니다. 완성도보다 반복 사용 가능성을 다음 단계 기준으로 삼았습니다.
PM's Role
03
PM의 역할은 실행 구조를 정의하는 것이다
기능을 늘리기보다 조직이 실제로 움직일 흐름을 정의했습니다. 기록, 판단, 액션 단계를 분리해 확장 여지를 남겼습니다.
Design Rationale
04
Rule-based를 선택한 이유
211건 수준의 데이터에서 ML 적용은 과설계로 판단하여 검증 가능한 기준을 먼저 확정하고, 데이터 누적 후 AI 판단 레이어로 교체 가능한 구조로 설계했습니다.
